> Архивный контракт v1: сохранён для совместимости и исторических проверок. Активное приложение обслуживает [v2.0](../docs/contracts-v2.md); инструкции ниже описывают только v1 и не определяют текущий API.

# CQA wire contract v1.0 — решение для интеграции

Единственный источник типов — `contracts/v1.py` (Pydantic v2). Машиночитаемые копии находятся в `contracts/schemas/`; обновляются командой `python -m contracts.export`. JSON Schema не выражает все межобъектные ограничения: backend также вызывает `validate_output`. Типы `src/domain/types.ts` — внутреннее представление UI, не контракт сети. Изменения этого каталога согласуются всеми тремя потоками до слияния; при несовместимом изменении повышается schema_version.

## Решения по пяти вопросам Дильназ

1. **Формат.** В сети snake_case. `type = binary | scale | flag`; `value` — строго целое число или null. Для binary/flag: 1 = Да, 0 = Нет; для scale только заданные `allowed_values`; null означает только допустимый N/A, никогда ошибку или неизвестность. `yes_no` не используем. В v1 шкалы имеют целые неотрицательные ступени от 0 до max. `weight` — десятичная строка, например `"15"`; итоги — строки `"85.38"`. Backend использует Decimal, ROUND_HALF_UP и округляет только итог. Веса не обязаны суммироваться до 100. Расчёт с нулевым знаменателем возвращает null + no_applicable_weight.
2. **Вызов Adalbala.** Python-адаптер внутри процесса FastAPI: `async evaluate(request: EvaluatorInput) -> AdapterResult`. Типизированный Protocol `Evaluator` уже в v1.py. Отдельный HTTP-микросервис и callback не нужны. Адаптер делает запрос к провайдеру; backend повторно валидирует ответ, проверяет доказательства, считает и сохраняет. Смена OpenAI/Gemini не меняет контракт. Provider failures переводятся backend в ErrorResponse, без секретов и полного ответа провайдера.
3. **message_id.** `{conversation_id}-m{index+1}`: первая реплика `p1-ru-001-m1`. Считаются ВСЕ реплики в исходном порядке, включая bot/system. Не сортировать по timestamp, не перенумеровывать после фильтра UI. Backend формирует ID один раз, остальные используют их. Evidence хранит ID, не индексы. ID уникальны внутри неизменяемой версии transcript; evaluation также хранит SHA-256 content_hash. Если текст/порядок меняется, старая оценка остаётся привязана к сохранённой старой версии. Фронтенд уже использует этот формат, менять его не надо.
4. **Ошибки.** Политика ниже обязательна. Ошибочная попытка может храниться в техническом журнале, но не как успешно завершённая оценка. Перепутанные типы и значения не приводим автоматически.
5. **Стек.** Целевой runtime Python 3.11; FastAPI + Pydantic v2 + SQLite, pytest и Hypothesis — подтверждены. Точные воспроизводимые зависимости общего backend фиксирует naki707 в lock-файле. Контрактные тесты не требуют запущенного FastAPI или API-ключа. Пока нет backend, используйте `requirements-contracts.txt`. Проверка: `python -m pytest tests/test_contracts.py -q`; CI также использует Python 3.11.

## Четыре основных схемы

| Файл | Назначение |
|---|---|
| schemas/checklist.schema.json | Неизменяемый чек-лист с id, version, channel и произвольным массивом критериев |
| schemas/model-output.schema.json | Только решения LLM: значение, объяснение, N/A и доказательства; без арифметики |
| schemas/evaluation.schema.json | Результат для UI с original/final, историей решений, provenance и серверными баллами |
| schemas/error.schema.json | Единая ошибка request_id + code/message/retryable/details |

Дополнительно: evaluation-job для асинхронного API и evaluator-input для Python-адаптера. При передаче схемы провайдеру используйте его schema helper/поддерживаемое подмножество JSON Schema. Не передавайте служебные метаданные `$schema`/title без проверки совместимости. Structural success не заменяет семантическую проверку.

## Запуск оценки и состояния

`POST /api/evaluations`: `{conversation_id, checklist_id, checklist_version}` → HTTP 202 и EvaluationJob со status=queued, evaluation=null, error=null. Имена в этом документе заменяют предварительный checklist_version_id из architecture.md. Воркер вызывает адаптер внутри приложения; `GET /api/evaluations/{id}` возвращает тот же job envelope.

- queued/running: evaluation=null, error=null.
- completed: evaluation заполнена, error=null; final содержит подтверждённый итог либо no_applicable_weight.
- needs_review: evaluation заполнена, error=null; total_score=null, provisional_total_score может содержать предварительную арифметику. UI явно показывает «Предварительно, требуется проверка».
- failed: evaluation=null, error содержит объяснение; подтверждённого или предварительного итога нет.

Ошибка синхронного клиентского запроса → HTTP 422 + ErrorResponse. Не найден объект → 404. Конфликт версии апелляции → 409. Ошибка уже принятой задачи приходит в job со status=failed; GET существующей задачи остаётся HTTP 200.

## Матрица валидации

| Ситуация | Поведение |
|---|---|
| Невалидный JSON/тип, пропущенный или повторный критерий, лишний criterion_id | MODEL_OUTPUT_INVALID; максимум один repair-вызов; затем failed без итога |
| Значение вне allowed_values, запрещённый N/A, нет причины N/A, противоречивые N/A-поля | То же: failed без итога после разрешённой попытки исправления |
| Неизвестный message_id, выдуманная цитата, пустое доказательство, неверный диапазон | Значения остаются кандидатами; evidence_status=unverified, needs_review, confirmed total=null; возможен один repair-вызов в пределах общего лимита |
| Timeout/429/5xx | До 2 попыток всего на job, учитывать Retry-After; явная provider error после исчерпания. Не подменять на 0/N/A |
| Отказ модели | MODEL_REFUSAL, failed; не представлять отказ как решение критерия |

Лимит — **не более двух вызовов провайдера суммарно на job**, включая HTTP retry и repair; не перемножать независимые retry-циклы. Полный повтор пользователем — новая задача с явной причиной. Нельзя автоматически переключить модель и выдать результат как прежнюю; provenance всегда отражает реальный provider/model.

Для `message`: минимум один ID. `quote` можно оставить null; сервер сам достаёт оригинал. Если quote передана, она должна быть точной непустой подстрокой единственной указанной реплики. Для `absence`: start/end задают включительный проверенный диапазон. Для N/A: причина + `not_applicable` и реплика либо диапазон. Отсутствие действия нельзя подтверждать придуманной цитатой. Проверка существования ссылки не доказывает смысловую правильность вывода.

№8 — `flag`, weight="0", max=1, allowed_values=[0,1], allow_na=false. При его непроверенном доказательстве critical_error=null; кандидат остаётся в results. В иных случаях critical_error определяется значением флага. Не расширять официальный перечень нарушений.

## UI и апелляции

UI делает явный mapper wire snake_case → внутренний camelCase. `Number(weight)` допустим для поля редактора/отображения, но итог и нормированные вклады UI получает от backend. Исходную Decimal-строку при неизменённом весе сохранять; новые веса отправлять строкой. JS `scoreEvaluation` не является источником окончательного итога после подключения backend.

Evaluation содержит `original` и `final`; до апелляции они одинаковы. original неизменяем. Каждое решение проверяющего добавляет запись decisions, повышает revision и пересчитывает final на сервере. `POST /api/appeals/{id}/decision` получает `{action, final_value, reason, expected_revision}`. Для confirm передаётся текущее значение; change снова проверяет шкалу и N/A. Конкурирующее устаревшее решение → 409 REVISION_CONFLICT. После ручного решения доказательство/диапазон также должны быть подтверждены или исправлены до снятия needs_review. Сохранять предыдущие ревизии и текст проверяющего; при нескольких апелляциях final строится поверх последних принятых решений каждого критерия. Флаг №8 меняет флаг, не числовой итог.

Для секций отдаём нормированный score каждой секции в 0..100 по применимым весам внутри секции. Эти проценты нельзя складывать для получения общего итога. Если секция содержит unverified criterion, её подтверждённый score=null; у секции без применимых весов тоже null. Общий total рассчитывается отдельно по всем применимым критериям.

`effective_weight` = 100 × weight / сумма применимых весов; `contribution` = effective_weight × value / max. Для N/A оба поля null. Передавать десятичные строки из расчёта без промежуточного округления; итог считать из исходных весов/значений, а не из округлённых отображаемых вкладов. Контекст Decimal — не менее 28 значащих цифр, ROUND_HALF_UP только при финальном quantize до 0.01.

## Приоритет источников

Этот контракт уточняет ранний архитектурный документ и задачи. Никакая существующая UI-структура автоматически не отменяет его. Если инженер уже сделал несовместимую реализацию, добавить явный mapper на границе; не менять silently смысл null, значения флага или тип веса.
