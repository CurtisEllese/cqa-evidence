# Капитан и тимлид: продуктовая точность, интеграция и сдача

Приоритет: **P0**. Задача: [#4](https://github.com/CurtisEllese/cqa-evidence/issues/4). Капитан — пользователь, продуктовый эксперт. Тимлид — ассистент в текущем чате. Это разные обязанности: эксперт подтверждает смысл и факты, тимлид проверяет реализацию и совместимость.

## Капитан — P0. Подтвердить критерии и ручные ответы

- [ ] Вместе с Roman выбрать 12–15 разнообразных DEV-диалогов RU/KZ/EN, включая звонки, N/A, незавершённый диалог, идентификацию, частичное решение и №8.
- [ ] Разметить каждый из восьми критериев: допустимое значение или N/A; короткая причина; message_id или проверенный диапазон; для N/A — условие применимости. Не смотреть оценку модели до своей разметки.
- [ ] Для №4 отделять «неполно ответил» от «фактически ошибся». Для продуктового утверждения записать источник. Если факт нельзя проверить, оставить экспертную неопределённость для согласования, не придумывать правильный ответ.
- [ ] Согласовать разногласия со вторым проверяющим; отдельную закрытую часть оставить Roman. Не считать уверенный ответ Gemini подтверждением продукта.

**Результат:** согласованные ручные решения, список спорных случаев и закрытая выборка. Рекомендуемый рабочий формат: conversation_id, criterion_id, value, applicability_reason, evidence_ids/checked_range, explanation, reviewer, reference_source. Для метрик переводит в строгий формат Adalbala.

## Капитан — P0. Организационные ответы

Уточнить у организаторов и зафиксировать в задаче:

1. Точное время выдачи контрольного набора и стоп-кода с часовым поясом.
2. Метрику сравнения: по критериям, общему баллу, N/A/№8 или комбинации.
3. Как получать контрольный group_id; формат и способ передачи результатов.
4. Куда отправить публичный репозиторий и как подтвердить получение ссылки.
5. Где доступны разрешённые продуктовые материалы и к какому продукту/юридическому лицу они относятся.

Ссылку организаторам отправляет капитан; наличие публичного репозитория само по себе не означает сдачу. Не возобновлять старый таймер «ещё 5 часов» без текущего расписания.

## Капитан — P1. Продуктовые факты

- [ ] Дать сначала 5–10 наиболее полезных проверенных фактов, затем расширять по ошибкам №4. Краткие факты полезнее большого несогласованного файла.
- [ ] Формат уже существует в KnowledgeFact: text, source, effective_date, product, jurisdiction, verified_by. Source — документ/раздел или доступная ссылка; effective_date — дата действия правила, а не автоматически сегодняшняя дата.
- [ ] Проверить актуальность, продукт и применимость. Не отправлять внутренние материалы в публичный репозиторий без права на публикацию; допустимый файл подключается локально на сервере.

**Результат:** файл для Дильназ и список случаев, где подтверждённых сведений недостаточно. Не требуется создавать полный справочник Freedom за хакатон.

## Тимлид — P0. Контракт и интеграция

- [ ] До каждого нового поручения проверять main, рабочие ветки, PR и задачи. Не объявлять работу в ветке уже доступной команде в main.
- [ ] Первым принять минимальное расширение groupId от Дильназ, затем UI Krutoi312. Источник типов — Pydantic, generated обновляются в том же PR. Не добавлять конкурирующие DTO.
- [ ] Ревью AI-исправления: отсутствие ответов по ID, отсутствие лишних правил, источник доказательства, исходные значения/шкалы/N/A, неизменный лимит попыток.
- [ ] Проверить хотя бы один полный сценарий с реальным провайдером в отдельной базе после интеграции. Тестовый transport в unit-тестах не выдавать за живой вызов.
- [ ] Сохранять совместимость: существующий запрос без groupId работает как DEV; старые оценки/апелляции не исчезают; интерфейс не считает итог сам.
- [ ] Перед объединением — contracts:check, pytest/JS, build; затем адресные проверки изменённого поведения. Зелёный CI не заменяет экспертную точность.

## P0. Выпуск и контрольный набор

- [ ] Roman подтверждает чистый запуск и матрицу обязательных сценариев. Любой незакрытый P0 отмечается явно; общий процент «готовности» не заменяет список блокеров.
- [ ] Перед стоп-кодом капитан подтверждает срок; тимлид фиксирует последний коммит/тег. В README записать модель, версию промпта, запуск, ограничения и измеренные результаты.
- [ ] При получении контрольной группы обработать новые данные зафиксированной системой. Не подставлять ответы по ID и не выдавать ручной пересмотр за исходную AI-оценку. Сдавать тот формат и вид результата, который требуют организаторы.
- [ ] Если новый загрузчик не успевает, использовать проверенный ручной импорт JSON; если исчерпана квота, фиксировать сбой и действовать по допустимому резерву, без фиктивных оценок.
- [ ] Репетиция защиты до 5 минут и резервное видео от Roman. После стоп-кода — только разрешённые организаторами действия с данными/настройками.

## Отдельно: бинго

Получить карточку всех девяти заданий; выполнить их, сделать девять реальных фото, добавить текст соответствующего задания и назвать файлы yourname_surname_bingo1 … bingo9. Уточнить личную/командную сдачу. Это отдельный организационный поток, выполнение которого приложение не подтверждает.

## Чего сейчас не делаем

Не добавляем второй провайдер, локальную LLM, риск-радар, CSI, сравнение операторов, новый фреймворк UI или обязательный двухпроходный pipeline. Приоритеты: точность → контрольные данные → проверяемый пользовательский сценарий → выпуск.
