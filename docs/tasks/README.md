## Границы совместной работы

1. Ветки создаём от актуального main; чужие незакоммиченные изменения не трогаем. Старый backend v1 не возвращаем.
2. Дильназ — единственный владелец изменения Pydantic/wire-контракта и generated-файлов. Krutoi312 — клиент API/mapper/UI. Adalbala — адаптер/промпт/eval. Roman — независимые тесты и приёмка. Конфликтующие файлы согласовать до правки.
3. Активный wire остаётся v2.0: yes_no, Decimal-строки, null для разрешённого N/A, существующие message_id. Новые groupId/checklistVersion — планируемые совместимые расширения; UI подключает их только после серверного коммита. В upstream query используется group_id.
4. Исходный ответ модели, ручное решение и финальный итог не смешиваем. Баллы считает сервер. Максимум две provider-попытки на задачу сохраняется; семантический двойной проход не добавляем без измеренного эффекта и согласования бюджета.
5. Нет блокировки одного потока ожиданием всего другого: frontend может подготовить форму, Roman — чистый запуск, капитан — разметку, пока backend готовит контракт. Заглушки в UI/тестах не являются завершённой интеграцией.

## Контрольные точки

Первое короткое обновление от каждого — ориентировочно через 20–30 минут после начала работы: ветка/коммит или PR, сделанное, результат проверки, блокер. Это интервал синхронизации, не обещание выполнить весь объём за полчаса. Фактический стоп-код уточняет капитан.

**Точка A:** контракт groupId согласован, семантический баг воспроизведён, первая разметка подготовлена, чистый запуск проверен.

**Точка B:** десять новых синтетических записей импортируются и оцениваются; проблемная тройка 5/2/0 исправлена; метрики части для разработки опубликованы. Резерв ручного импорта работает независимо от новой загрузки.

**Точка C:** интегрированный main проходит тесты и живой сценарий; Roman проверяет закрытую выборку, аудио и демонстрацию; капитан знает формат сдачи. Невыполненные проверки перечислены явно.

**Перед стоп-кодом:** прекратить расширение функций, исправить блокеры, зафиксировать SHA/тег и резерв. Если времени мало, надёжный ручной импорт лучше недоделанного загрузчика, но P0-ограничение нужно отразить честно.

## Общая приёмка PR

- Ссылка на задачу, конкретное изменение поведения, проверенные случаи, результаты команд и оставшиеся ограничения.
- Генерация контрактов согласована; npm test и production build проходят. Для LLM — отдельный отчёт реальных вызовов; мок не подтверждает точность.
- Нет секретов, реальных клиентских транскриптов, аудио, SQLite или приватной разметки в публичном Git. Публикуются синтетические воспроизведения и агрегаты.
- Объединение после ревью тимлида. Готовность означает проверенный результат в main, а не только сообщение «запушил ветку».

Подробные требования живут в соответствующих файлах; GitHub issues содержат их копии. При согласованном изменении объёма обновлять и файл, и задачу, не рассылать противоречивые версии в отдельных сообщениях.
