# Durable batch acceptance

Дата: 2026-11-08, Asia/Qyzylorda. Авторская область: серверная очередь и её подключение в интерфейсе.

## Результат

Очередь перенесена из браузерного цикла в SQLite. Сервер хранит ID запуска, набор, состав, сохранённую версию и снимок чек-листа, отдельные снимки запросов оценщика, состояние каждого элемента и прогресс. Закрытие страницы, reload и переход между разделами не запускают новые оценки и не прекращают серверную очередь.

Платных вызовов в этой работе: **0**. Все проверки использовали отдельные временные базы и fake evaluator/MockTransport. Рабочая SQLite, `.env.local`, результаты DEV, лимит бюджета и настройки реальной модели не изменялись. Сервер на порту 8000 не перезапускался. Публикаций, Telegram, commit/push/reset/checkout не было.

## Серверные гарантии

- Создание очереди, всех `evaluation_jobs` и `batch_items` выполняется в одной `BEGIN IMMEDIATE` транзакции. Неуспешная проверка участника откатывает весь запуск.
- `requestId` имеет постоянную привязку к запуску. Одинаковый состав, набор, версия и `expectedRevision` объединяются даже при разных ключах из двух вкладок. Ключи таких повторных запросов тоже сохраняются. Повтор после завершения возвращает прежний запуск; изменение тела при том же ключе — 409.
- Новый запуск требует актуальную ревизию рабочего пространства. Это исключает повторную оплату из устаревшей вкладки после завершения предыдущего запуска. Осознанная новая переоценка с обновлённым состоянием остаётся возможной.
- Перед I/O сохраняется захват элемента; `EvaluationService.run()` атомарно переводит только `queued` в `running`. Повторное планирование того же job не вызывает оценщик.
- Для batch установлен **один вызов адаптера на элемент**, без автоматических retry и repair. Одиночная оценка сохраняет прежний режим repair/retry, проверку доказательств, расчёт баллов и бюджетный адаптер.
- `stop` завершает текущий захваченный диалог и приостанавливает оставшиеся. `resume` использует тот же batch ID и исходные снимки, отправляет только `queued`. Проверка ревизии не позволяет запоздалому resume отменить более новую остановку.
- `cancel` отменяет только ещё не отправленные элементы и согласованно завершает их `evaluation_jobs`. История сохраняется, текущий запрос завершается. После этого можно запустить другой набор или одиночную оценку.
- Ошибки бюджета/провайдера останавливают дальнейшую очередь. Неопределённые исходы не повторяются при resume и исключены из обычного массового запуска/«Повторить ошибки» **как в UI, так и при прямом POST**.
- В частности, исправлен выявленный QA случай **`PROVIDER_UNAVAILABLE`**. Нынешний адаптер объединяет под этим кодом транспортные обрывы и другие ошибки, поэтому очередь консервативно считает его `uncertain`. Все `PROVIDER_*`, кроме подтверждённого `PROVIDER_RATE_LIMIT`, также считаются неопределёнными; это включает `PROVIDER_CONNECTION_ERROR` и `PROVIDER_TIMEOUT`. `EVALUATOR_ERROR`, `BATCH_OUTCOME_UNKNOWN`, `WORKER_INTERRUPTED` тоже блокируют массовый повтор.
- Набор проверяется сервером: ID должны входить в выбранный сохранённый набор. Проверяются активность, hash и апелляции. При изменении контекста перед отправкой и batch item, и evaluation job переходят в терминальную ошибку, без платного вызова. Апелляция, появившаяся во время запроса, запрещает применение новой оценки.

## Политика перезапуска

1. Один backend worker владеет локальной БД в течение всего lifespan. OS file lock не позволяет второму серверу выполнить recovery живого worker. Путь lock нормализован; файл остаётся на диске, блокировка освобождается ОС при завершении процесса.
2. После рестарта оставшиеся, ещё не отправленные элементы сохраняются `queued`; очередь становится `paused`. Автоматического продолжения нет.
3. Если результат уже записан в `evaluations`, но прогресс batch ещё не записан, recovery восстанавливает `completed` без вызова оценщика.
4. Захваченный элемент без подтверждённого сохранённого результата становится `uncertain`, связанный job — `failed` с `BATCH_OUTCOME_UNKNOWN`, `retryable=false`. Даже авария между захватом и отправкой трактуется консервативно.
5. Пользователь может продолжить только оставшиеся или отменить их. Неопределённый диалог требует сверки результата/расходов перед явной отдельной переоценкой. Его обычный массовый повтор сервер отклоняет.

Это гарантия отсутствия автоматического повторного вызова, а не обещание exactly-once выполнения у внешнего провайдера. Удалённый результат при разрыве соединения может быть неизвестен; резерв бюджета не освобождается этим модулем.

## API и интерфейс

- `POST /api/batches`: `requestId`, `group` (`workspace:` или `group:<id>`), `conversationIds`, `checklistVersion`, `expectedRevision`.
- `GET /api/batches/current`, `GET /api/batches/{id}`: сохранённый запуск и поэлементный прогресс.
- `POST /api/batches/{id}/stop|resume|cancel`: команда с `expectedRevision`.
- Контракты v2 созданы в Pydantic; JSON Schema и TypeScript сгенерированы штатным генератором.
- StoreProvider наблюдает очередь через GET. Mount/reload/unmount и переходы не отправляют POST и не управляют выполнением worker. Наблюдение восстанавливается после сетевой ошибки.
- Прогресс принимается монотонно по ревизии; результаты рабочего пространства повторно загружаются после успешной синхронизации, в том числе после временной ошибки загрузки результатов.
- В блоке очереди доступны stop/resume/cancel; неопределённые результаты показаны отдельно. Заголовки диалогов используют общий `conversationTitle`. Внешний вид одиночной переоценки не менялся.
- Общая `/api/*` граница сохранена. После передачи `app.py`/`api.ts` чат доступа подключил свой middleware; финальный браузерный прогон работает с этим подключением в локальном режиме.

### Реальный браузер

`python tests/browser_durable_batch.py` — **passed**, Chromium headless, реальный FastAPI + SQLite на выделенном случайном loopback порту, fake evaluator с управляемым ожиданием. Не перехват API вместо сервера.

1. Reload сохраняет тот же batch ID, группу и прогресс; новых POST и вызовов оценщика нет.
2. Навигация обзор → диалоги подключается к тому же запуску.
3. Вторая вкладка и повторные POST с одинаковым/другим requestId не создают второй batch или вызов.
4. Stop даёт закончить один текущий диалог; после reload доступны ровно два оставшихся.
5. Обе страницы закрываются после resume; сервер завершает очередь, новая страница показывает 3/3.
6. Во втором, явно запущенном наборе процесс backend аварийно завершается во время fake-provider I/O. После рестарта первый элемент `uncertain`, остальные `queued`; повтор старого POST не продолжает очередь. Явный resume отправляет только два оставшихся.
7. Неопределённый результат исключён из режима «Все доступные».

Журнал показывает **ровно 6 fake вызовов для двух сознательно запущенных наборов по 3 диалога**, каждый ID — ровно дважды суммарно. Неподтверждённый первый элемент второго запуска не вызывался в третий раз. `pageErrors=[]`, `paidCalls=0`.

## Ограничения

- Поддерживается один процесс приложения на одну локальную SQLite; второй намеренно не запускается. Redis и внешний job broker не добавлены.
- Один batch — до 1000 уникальных ID; очередь сериализована. Неотправленная paused очередь освобождается действием «Отменить оставшиеся».
- UI показывает текущий/последний запуск. Предыдущие batch и результаты остаются в БД и доступны по batch ID; отдельный экран истории запусков не добавлялся.
- Реальный API, реальное списание и фактическая связь с провайдером не проверялись по запрету расходов. Доказательства основаны на сохранённых попытках, fake call counter, реальном worker/restart и SQLite.
- Нет ручного «считать неопределённый запрос безопасным» в массовом API. После сверки остаётся отдельная переоценка; это сознательная защита от повторной оплаты.
