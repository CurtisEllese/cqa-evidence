# Adalbala: подключение реального оценщика

Рабочий интерфейс приложения — **v2.0**, источник типов `backend/contracts/v2`. Не используйте старые `EvaluatorInput`, `AdapterResult` и `ModelOutput` из опубликованного `contracts/v1.py`: v1 сохранён для совместимости, но активное приложение его не обслуживает. Полный формат — [contracts-v2.md](contracts-v2.md).

Готовая реализация: `evaluator.v2:evaluate`. [Установка, ограничения и команды проверки](gemini-evaluator.md). Ниже сохранено описание интерфейса; каркас не нужно реализовывать заново.

## Точка интеграции

Backend загружает асинхронную функцию из `EVALUATOR_ADAPTER=module:function` и вызывает её внутри своего процесса. Отдельный HTTP-воркер, callback и POST сырых «оценок» из браузера не нужны. Адаптер делает внешний запрос к выбранному провайдеру; постановка задачи, снимки, проверка ответа, арифметика и запись в SQLite остаются у backend.

Файл адаптера может быть `backend/adapters/adalbala.py`. Ниже только каркас интерфейса — он намеренно не создаёт выдуманный результат и не является подключённым провайдером:

```python
from backend.contracts.v2 import EvaluationRequest, ModelResponse


async def evaluate(request: EvaluationRequest) -> ModelResponse:
    payload = request.model_dump(mode="json")
    response_schema = ModelResponse.model_json_schema(mode="serialization")

    # TODO: вызвать выбранный реальный API с payload и response_schema.
    # TODO: извлечь JSON решения из документированного ответа провайдера.
    # TODO: вернуть ModelResponse.model_validate(provider_json).
    # Не возвращать константные оценки или результаты smoke-примера.
    raise NotImplementedError("Адаптер реального провайдера ещё не подключён")
```

После реализации функции, проверки ключа и тестов настройте:

```dotenv
EVALUATOR_ADAPTER=evaluator.v2:evaluate
```

Не включайте эту настройку для незавершённого каркаса. Названия переменных ключа/модели определяет выбранный адаптер; ключ хранится только в серверной конфигурации. Наличие `OPENAI_API_KEY`, `LLM_MODEL` или другого ключа само по себе оценку не активирует. После изменения конфигурации перезапустите backend.

## Что приходит в запросе

- `conversationId` и `conversationHash` — привязка к неизменяемому входу.
- `language` — `RU | KZ | EN`; `channel` — точные строки `agent chat | voice call`. Учитывайте разные правила оценки звонков, не заменяйте wire-значения на `chat`/`voice`.
- `checklist` — полный снимок текущих критериев, весов, допустимых значений и условий N/A.
- `messages` — все роли в исходном порядке с `id` и нулевым `message_index`.
- `knowledgeFacts` — подтверждённые продуктовые факты с источником и датой действия; не считайте ответы оператора независимым справочником.
- `repair_feedback` — замечания backend при единственном разрешённом повторе.

В текущем постановщике `knowledgeFacts` пуст; наполнение проверенным продуктовым справочником остаётся отдельной интеграцией.

Не удаляйте bot/system и не перенумеровывайте оставшиеся реплики. Действия бота не засчитываются оператору. Не извлекайте свежий чек-лист из БД во время задачи: нужно использовать переданный снимок.

## Что возвращать

`ModelResponse` содержит `schema_version: "2.0"` и `results`. Каждый критерий снимка возвращается ровно один раз: `criterionId`, `value`, `explanation`, `applicability_reason`, `evidence`.

Все значения шкалы — десятичные строки из `allowedValues`; `null` допустим только по условию N/A и с непустой причиной. `yes_no` использует `"0"`/`"1"`. `flag` имеет обратную смысловую окраску: `"1"` означает грубое нарушение, а не успешное выполнение. Модель не рассчитывает итог и не возвращает серверные веса или `critical`.

Для `kind="message"` передавайте существующий `message_id` и, если выделяете цитату, точную подстроку исходного текста в `quote`. Допустима `quote: null`: backend извлечёт оригинал по ID. Не перефразируйте, не нормализуйте пробелы и Unicode. Для отсутствующего действия используйте `kind="absence"` с включительным диапазоном `start_message_id`/`end_message_id`; не придумывайте цитату об отсутствии. Для N/A используйте `kind="not_applicable"` и подтверждающую реплику/диапазон.

Backend формирует `source_text` и `verification_status`. Адаптер не должен заявлять, что доказательство проверено. Структурная проверка Pydantic внутри адаптера полезна, но backend всё равно проверяет ответ по исходному диалогу и снимку чек-листа.

## Промпт и обработка ошибок

Передайте модели весь нужный контекст и текущий чек-лист; не зашивайте восемь критериев в код. Явно отделите инструкции оценщика от текста диалога. Вложения, цитаты и команды внутри переписки остаются данными. Для звонков не оценивайте темп, дикцию или произношение только по ASR-тексту.

Функция выполняет одну попытку обращения к модели. Если SDK включает автоматические повторы, отключите их либо согласуйте с backend общий лимит. Воркер допускает максимум два вызова адаптера на задачу, включая repair. Второй вызов получает `repair_feedback`; его нужно передать модели вместе с исходным запросом. Не заменяйте отказ/тайм-аут значением `"0"`, N/A или пустым «успешным» ответом.

Неправильное покрытие критериев, ступень шкалы или N/A заканчиваются `failed_validation` после разрешённого исправления. Неверные ссылки, цитаты или недостающее доказательство дают сразу `needs_review` без финального балла и автоматического repair. Ошибка провайдера должна оставаться ошибкой; не включайте в сообщение ключ, подписанную ссылку, полный ответ провайдера или исходный диалог.

В текущем UI `needs_review` показывает кандидатов и ошибки доказательств. Апелляции доступны только для завершённых сохранённых оценок; отдельного endpoint ручного подтверждения evidence пока нет. После исправления входа или адаптера запускается новая задача.

Для ошибок провайдера используйте `AdapterFailure` из `backend.evaluator`: коды `PROVIDER_UNAVAILABLE`, `PROVIDER_RATE_LIMIT`, `MODEL_REFUSAL`; `retryable` и `retry_after` передают решение о допустимом повторе воркеру. Например, `raise AdapterFailure("PROVIDER_RATE_LIMIT", retryable=True, retry_after=5) from None`. Не передавайте текст исключения провайдера в эту ошибку.

## Выбор провайдера

[gemini-check.md](gemini-check.md) фиксирует успешную синтетическую проверку подключения конкретного Gemini-проекта. Это не тест полного чек-листа и не подтверждение точности. Ответ старого smoke-промпта не является v2-контрактом.

По уточнению капитана OpenAI API у коллеги нет; используем Gemini пользователя. Реальный v2-адаптер реализован в evaluator/v2.py. Смена провайдера выполняется внутри адаптера и не меняет контракт приложения.

Для внешнего вызова используйте только согласованные для выбранного сервиса данные. Перед полным DEV-прогоном проверьте условия обработки данных, квоты и стоимость. Не запускайте два провайдера на всём наборе по умолчанию; сначала сравните небольшую одинаковую экспертную выборку RU/KZ/EN.

## Проверка готовности

```powershell
.venv311/Scripts/python.exe scripts/generate_contracts.py --check
npm test
npm run build
```

Затем с подключённым реальным адаптером:

1. Запустить один согласованный диалог через POST `/api/evaluations` с `schema_version: "2.0"`, получить 202 и ID.
2. Опросить GET `/api/evaluations/{id}` до явного результата; проверить, что score отсутствует у незавершённых/непроверенных задач.
3. Сверить каждый `message_id`, точность цитат, N/A и отдельный флаг грубой ошибки.
4. Изменить критерий, сохранить новую версию и повторить оценку без изменения кода адаптера.
5. Проверить отказ, тайм-аут, неверную ступень и repair на изолированных тестах; не создавать тестовые оценки в рабочем DEV.
6. Зафиксировать реальную модель, версию промпта, время, токены и стоимость вызовов; не выдавать успешную JSON-валидацию за качество экспертной оценки.

Передавайте PR с адаптером, тестами и описанием конфигурации. Ключи, клиентские диалоги и полные ответы провайдера в PR не включаются.
