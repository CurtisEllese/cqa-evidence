## Решение тимлида

**Рабочее приложение уже собрано. Главный незакрытый риск — смысловая точность оценки и готовность к контрольному набору.** Переписывать backend, интерфейс или подключение модели не нужно. Следующий этап — исправить воспроизводимую ошибку применения нового критерия, измерить ошибки на ручной разметке и закрыть загрузку контрольного `group_id`.

В живой проверке модель добавила требование, которого нет в пользовательском критерии. Поэтому зелёные тесты и успешное подключение API пока не позволяют заявлять готовность к сравнению с Ground Truth.

## Найденные проблемы и критерии исправления

### P0 — модель добавляет правила сверх критерия

В UI задано: «5 — оператор дал шаги и клиент подтвердил решение; 2 — шаги даны без подтверждения; 0 — шагов нет. Приветствие и представление не учитывайте».

Оператор дал шаги. Клиент ответил: `I found it, thank you. That solved my question.` Модель вернула **2**, объяснив, что подтверждение было самостоятельным, а не после прямого запроса оператора. Условия о запросе подтверждения в критерии нет. Ответ прошёл схему и Evidence Guard; итог стал **90.77** вместо 100 при неизменных остальных результатах.

Воспроизводимый синтетический пример: [audit/custom-criterion-repro.json](audit/custom-criterion-repro.json). В нём эталон задан только для проверяемого нового критерия; остальные ответы модели не объявлены экспертной разметкой.

**Приёмка:** этот пример даёт 5; вариант без подтверждения — 2; без шагов — 0. После изменения промпта перепроверить независимые новые критерии и исходную рубрику. Не прописывать ответ по ID/названию теста. Само наличие фразы «не выдумывай» уже не решило проблему.

### P0 — неизвестна точность на DEV и скрытых данных

В репозитории есть план eval и синтетический smoke, но нет подтверждённой ручной DEV-разметки с MAE, совпадением критериев, ошибками N/A и №8. «100 баллов за диалог» не означает «100% точности системы».

**Приёмка:** 12–15 разнообразных примеров RU/KZ/EN, включая звонки и пограничные случаи; независимые оценки двух участников с согласованием разногласий. Часть — для настройки, часть не использовать при настройке. Показать число примеров, ошибки по критериям/языкам, MAE итога и отдельно №8. Похожие переводы одного сценария держать в одной части. Реальные записи хранить вне публичного Git; в отчёт — агрегаты и разрешённые обезличенные примеры.

### P0 — контрольный group_id не поддержан текущим обновлением

`backend/app.py` принудительно подставляет `group_id=DEV`; `Repository.replace_dev` принимает только DEV из ровно 65 записей. Замена значения в серверной ссылке сама по себе не поможет. В UI только «Обновить DEV».

**Приёмка:** поле group_id → серверный запрос без раскрытия подписанного URL → набор произвольного допустимого размера, например 10 → оценка/экспорт без изменения кода. Не потерять предыдущие наборы и оценки. Резерв уже есть: вручную получить JSON контрольного набора и загрузить его через импорт; этот путь надо отрепетировать до стоп-кода.

### P1 — продуктовые факты и семантическая проверка

`backend/evaluator.py` передаёт `knowledgeFacts=[]`. Система не располагает подтверждённым справочником Freedom; уверенность по №4 нельзя принимать за проверку фактической правильности.

**Приёмка:** пользователь передаёт проверенные факты с источником, датой и применимостью; backend добавляет их в снимок запроса, модель ссылается на них. При отсутствии факта честно описывать неопределённость, не превращать её в N/A и не придумывать тарифы/сроки. Начать с компактного JSON, без отдельной векторной БД.

### P1 — выбор чек-листа и демонстрация истории

Сейчас API старта принимает только conversationId, а сервер выбирает последнюю конфигурацию. Нельзя выбрать отдельный чек-лист звонков/чатов или старую версию. Старые оценки сохранены и доступны по ID, но удобного переключателя истории оценок нет; UI показывает историю апелляций.

**Приёмка:** явно выбрать сохранённый чек-лист/версию при запуске; старый результат остаётся доступен. Согласовать минимальное изменение v2 через Pydantic и генератор. Для демонстрации новой версии до исправления использовать новый диалог без апелляций: старый с апелляцией намеренно заблокирован для переоценки.

### P1 — UX и оставшаяся приёмка

- Выравнять язык `explanation` и `applicability_reason` с языком диалога; проверить EN и KZ отдельно. Не переводить исходный транскрипт.
- Добавить переход от evidence звонка к аудиопозиции, с проверенным смещением ISO-времени; не обещать точную синхронизацию без проверки.
- Для needs_review либо завершить ручное подтверждение evidence, либо честно оставить просмотр кандидатов и повтор. Сейчас это не готовая очередь ручного принятия решения.
- Исправить текст пустого dashboard: он предлагает подключить ИИ даже при работающем адаптере. Ручные записи тоже помечены DEV в навигации.
- На втором компьютере прогнать README, запись, импорт нового набора, изменённый критерий, апелляцию, экспорт и перезапуск. Проверить доступную квоту непосредственно перед защитой.
- Зафиксировать модель/промпт и условия API. Для платного режима добавить стоимость всех попыток; сейчас денежная стоимость не рассчитывается.

## Порядок до сдачи

1. Сейчас: всем обновиться от main; не разрабатывать второй backend/адаптер. Параллельно начать разметку и исправление group_id. Точный остаток времени сверить отдельно: прежние «5 часов» не являются текущим таймером.
2. Первая контрольная точка: исправленный пример нового критерия + пакет из 10 новых синтетических записей импортируется/оценивается/выгружается. Показать метрики хотя бы первой согласованной выборки.
3. Вторая: запуск на другом ноутбуке, новый диалог → evidence → апелляция → новая версия на другом диалоге. Все объяснения доступны проверяющему, нет фиктивных нулей при API-ошибке.
4. До стоп-кода: исправлять блокеры и точность; зафиксировать SHA/тег, проверить резервную базу через SQLite backup, сохранить разрешённое видео демо. Ссылку организаторам отправить по их формату.
5. Защита до 5 минут: 1 минута интерфейс/диалог, 2 минуты оценка/evidence/N/A, 1 минута апелляция, 1 минута изменение критерия. Указать измеренные ограничения, а не обещанную точность.

Не добавляем сейчас риск-радар, CSI-корреляцию, сравнение операторов, второй провайдер, локальную LLM или обязательный двойной проход. Частичный пересчёт одного критерия и «до → после» по всему набору тоже пока не реализованы и не должны вытеснять контрольный сценарий и проверку точности.

Бинго — отдельная организационная задача: девять настоящих фото с текстом задания и правильными именами. Репозиторий не подтверждает её выполнение. Карточка всех девяти заданий и факт сдачи ещё не зафиксированы.
