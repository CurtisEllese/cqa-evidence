# Подтверждённые факты и сохранённая версия: backend P1 / задача #2

Этот PR добавляет загрузку утверждённого локального справочника и выбор версии
одного чек-листа. Расчёт, модель, промпт, лимит попыток и решения апелляций остаются
прежними. P0-загрузка групп передана отдельно в PR #9; эта работа от неё не зависит.

## Файл фактов

Капитан готовит массив записей существующего `KnowledgeFact`. Все шесть полей
обязательны: `text`, `source`, `effective_date`, `product`, `jurisdiction`, `verified_by`.
Дата действия — реальная календарная дата в формате YYYY-MM-DD; дата просмотра
страницы не заменяет дату действия. Лишние поля и отсутствующие значения отклоняются.

Формат показан **только на вымышленном примере**, не правиле Freedom:

```json
[
  {
    "text": "Учебный отчёт тестового продукта находится в разделе «Тестовые отчёты».",
    "source": "https://example.invalid/synthetic-product/report",
    "effective_date": "2026-01-01",
    "product": "Synthetic test product",
    "jurisdiction": "Synthetic test scope",
    "verified_by": "Synthetic test reviewer; not expert approval"
  }
]
```

Синтетический файл для автотестов лежит в `backend/tests/fixtures/knowledge-facts.synthetic.json`.
Не подключать его к оценке реальных диалогов. `docs/product/knowledge-candidates.json`
использует отдельную схему проверки источников: загрузчик намеренно его отклоняет.
Мы не преобразуем кандидатов автоматически, не подставляем неизвестные даты,
юрисдикции или имя эксперта. Проверка структуры не подтверждает истинность факта.

После получения утверждённого файла положить его в приватный `local-data` и задать
в `.env.local`:

```dotenv
KNOWLEDGE_FACTS_PATH=./local-data/knowledge-approved.json
```

Относительный путь считается от корня репозитория; абсолютный также допустим.
Значение по умолчанию пустое: `knowledgeFacts=[]`. Текст фактов не принимается от
браузера. Файл читается при создании приложения, UTF-8 с BOM или без него; предел
1 МБ проверяется до разбора. Указанный, но отсутствующий/нечитаемый/повреждённый файл
даёт `KnowledgeConfigurationError` до создания базы или подключения оценщика.
Ошибка не печатает содержимое файла. Корректный массив `[]` разрешён.

Применимость к продукту, юридическому лицу и периоду подтверждает капитан.
Backend передаёт весь утверждённый набор с этими полями: он не умеет определять
продукт/юрисдикцию конкретного диалога, соответствующих полей в импорте нет.
Применение фактов к содержанию диалога проверяет Adalbala вместе с экспертом.
Отсутствие подходящего факта не должно автоматически становиться N/A или ошибкой
оператора; это правило работы оценщика, не дополнительная серверная формула.

## Снимки и обновление

`EvaluationService` получает отдельную копию загруженных фактов. При создании
задачи факты, сообщения и выбранный чек-лист вместе записываются в
`evaluation_jobs.request` как `EvaluationRequest`. Это не новый wire-формат.
Каждая попытка получает свою копию снимка; изменение объекта адаптером не влияет
на repair и не переписывает исходный запрос.

Для обновления файла перезапустить backend. Новые задачи после перезапуска получат
новые факты; уже сохранённые запросы и результаты не изменятся. Редактирование
файла при работающем сервере не действует до перезапуска. Hot reload, новый API
управления справочником и дополнительная БД не добавлены.

## Выбор версии для frontend

`GET /api/checklists` уже возвращает сохранённые версии. В начале оценки передать:

```sh
curl -sS http://127.0.0.1:8000/api/checklists
curl -sS http://127.0.0.1:8000/api/evaluations -H 'Content-Type: application/json' -d '{"schema_version":"2.0","conversationId":"ACTUAL_CONVERSATION_ID","checklistVersion":1}'
```

Заменить ID на существующий диалог. Ответ — прежний 202 с ID задачи и выбранным
`checklist`; затем `GET /api/evaluations/{id}`. Без поля или с null — последняя
сохранённая версия в момент создания задачи. Несуществующая версия — 404, неверный
тип/диапазон — 422, без вызова модели и записи задачи. Версия передаётся integer,
а баллы/веса по-прежнему Decimal-строками.

Во время обработки UI показывает версию **задачи**, а не глобальную текущую.
В JSON Schema и `src/generated/contracts.ts` поле сгенерировано из Pydantic.
UI-селектор делает Krutoi312; здесь его нет.

Важное уточнение аудита: прежняя блокировка переоценки после апелляции находилась
в UI, но отсутствовала в `EvaluationService.create`. Теперь этот же запрет действует
на сервере для pending/accepted/rejected и любой выбранной версии. Ответ — 409
`CONFLICT`; исходные оценки/решения сохраняются. Активную задачу тоже нельзя обойти
сменой версии. Расширять историю переоценок после апелляции этот PR не пытается.

## Проверка

```sh
npm run contracts:check
npm test
npm run build
```

Для адресного прогона: `.venv/bin/python -m pytest backend/tests/test_knowledge.py backend/tests/test_evaluation_context.py -q`
(Windows: `.venv311/Scripts/python.exe`). Проверяется загрузка, ошибка конфигурации,
передача всех полей адаптеру, сохранность после изменения файла/перезапуска/repair,
выбор старой версии после появления новой шкалы, неизменность старого результата,
отсутствие вызовов на неверных запросах и защита апелляций.

Все вызовы модели в этих тестах синтетические. Живой Gemini, истинность продуктовых
сведений, качество их применения и UI-приёмка остаются отдельной проверкой команды.
