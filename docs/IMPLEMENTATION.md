# Реализация и границы готовности

Основной контур: React/TypeScript/Vite → FastAPI/Pydantic → SQLite. Официальный чек-лист находится в `backend/rubric.json`. Нормализация, проверка значений, доказательств и итоговая арифметика принадлежат серверу.

## Данные и интерфейс

- DEV содержит 65 диалогов: 60 чатов и 5 звонков, RU 35 / KZ 15 / EN 15. В наборе нет эталонных оценок.
- Импорт, экспорт, сохранение версий чек-листа и решения апелляций проходят через API и транзакции SQLite.
- Оценка сохраняет свою версию чек-листа; апелляция не переписывает исходный результат.
- Аудиопрокси разрешает HTML-плееры организатора, передаёт диапазоны байтов и закрывает upstream-соединения при завершении или отключении браузера.
- Клиент хранит черновики и временный снимок для отображения; итоговые баллы и постоянные данные не вычисляются и не сохраняются в localStorage.

## Контракт и оценщик

Активный формат приложения — [v2.0](contracts-v2.md): Pydantic в `backend/contracts/v2`, сгенерированные JSON Schema в `contracts/v2` и TypeScript в `src/generated/contracts.ts`. Опубликованный `contracts/v1.py` остаётся замороженным; тесты v1 сохраняют его совместимость, но приложение обслуживает только v2.

Интеграция адаптера описана в [ADALBALA.md](ADALBALA.md), маршруты и ответственность — в [TEAM-HANDOFF.md](TEAM-HANDOFF.md).

Gemini-адаптер реализован и объединён в main: `evaluator.v2:evaluate`. Настройка сервера и результаты живых проверок описаны в [gemini-evaluator.md](gemini-evaluator.md). Для запуска нужны серверный ключ и конфигурация модели. При отсутствии адаптера запуск оценки возвращает 503. Тестовая реализация оценщика допустима только в изолированных тестах; рабочие DEV-диалоги нельзя заполнять синтетическими баллами.

`needs_review` показывает кандидатов без итогового балла. Ручное подтверждение evidence отдельным API пока не реализовано; апелляции доступны для завершённых сохранённых оценок. После исправления входа или адаптера непроверенный случай запускается новой задачей.

Актуальная приёмка и найденные ограничения описаны в [командном аудите](team-audit-2026-11-07.md). Реальный вызов Gemini через UI подтверждён; независимая точность ещё не измерена, а проверка нового критерия выявила добавленное моделью условие. OpenAI API не подключён.

## Проверки

Установка и команды запуска находятся в [README](../README.md). Минимальный набор проверяет актуальность сгенерированных контрактов, Python-тесты и сборку TypeScript/Vite. Property-based тесты проверяют инварианты шкал и расчёта; обычные тесты — API, SQLite, задания и аудио. Успех генерации схем не заменяет проверку межобъектных правил и доказательств.

Браузерная проверка `tests/browser_smoke.py` использует отдельные процессы и временную базу в `tmp/qa`. Дополнительно нужны Playwright и Chromium; проверки реального аудио зависят от доступности организатора. Синтетические оценки создаются только в изолированной базе. Отчёты и снимки не публикуются в Git.

Результаты последнего запуска следует брать из вывода тестов/CI, а не из накопительного числа в этом документе. Наличие теста не является доказательством точности LLM.

## Что остаётся до полноценной демонстрации

1. Исправить смысловую ошибку применения нового критерия и поддержать контрольный group_id; воспроизводимый пример и приоритеты — в командном аудите.
2. Выполнить экспертную калибровку RU/KZ/EN и сверить сложные случаи N/A, отсутствие действий и грубые ошибки.
3. Зафиксировать модель, версию промпта, затраты и время полного прогона.
4. Проверить сквозной сценарий: новый диалог → задача → проверенная оценка → доказательство → апелляция → экспорт.

Публичное размещение дополнительно требует авторизации, прав доступа, HTTPS и резервного копирования. Эти функции не подменяются текущими ограничениями localhost/Origin.
