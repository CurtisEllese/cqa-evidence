# Интеграция контрольных групп и проверяемой оценки

Эта поставка объединяет main `15ef8ea`, PR #9 (`ee26e40`), PR #10 (`5ef13ce`)
и UI-ветку `codex/dataset-group-ui` (`7b71d43`). В конфликте `backend/app.py`
сохранены оба импорта: `MAX_IMPORT_BYTES` и `load_knowledge_facts`.
Текущий адаптер OpenAI/Luna, арифметика и правила апелляций сохранены.
Публикация PR не означает, что он уже объединён в main.

## Поведение

- Импорт группы и файл проверенных фактов работают вместе с выбором сохранённого чек-листа.
- В списке есть фильтр «Грубые ошибки»: исходная завершённая AI-оценка определяет
  «Есть» / «Не выявлены». Отсутствующая оценка, queued/running, needs_review и ошибки
  относятся к «Нет подтверждённой оценки». Фильтрация выполняется до пагинации,
  сочетается с языком/каналом и возвращает на первую страницу.
- Принятая апелляция не скрывает исходное обнаружение. В списке обозначено изменение
  флага; в карточке отдельно показаны первоначальные объяснение и доказательство.
  Номер критерия не зашит: используются серверный флаг и исходные результаты.
- Список версий загружается существующим GET `/api/checklists`.
  По умолчанию выбирается последняя сохранённая версия. POST `/api/evaluations`
  передаёт выбранный `checklistVersion`; прежние запросы без этого поля совместимы.
  Карточка результата всегда показывает снимок версии задачи. Выбор версии для
  следующей оценки не меняет прежний результат.
- Пока каталог версий загружается или недоступен, запуск блокируется. Ошибка видна,
  есть повторная загрузка. Во время оценки выбор и кнопка заблокированы; существующий
  механизм tracking/polling не создаёт второй job по повторному клику.
- Любая история апелляций этого диалога блокирует переоценку и на сервере, и в UI;
  интерфейс объясняет причину. Это прежняя политика backend из #10.
- При подключённой модели пустой dashboard предлагает открыть диалог и запустить
  оценку; сообщение «подключите ИИ» показывается только без адаптера.

## Структура

`src/features/criticalStatus.ts` определяет три состояния исходного флага без I/O
и без расчёта баллов. `EvaluationControls.tsx` управляет только загрузкой/выбором
версии и доступностью кнопки. HTTP и wire-преобразование остаются в `services/api.ts`,
задания и polling — в существующем store, окончательная арифметика — в backend.
Новых runtime-зависимостей и конкурирующих DTO нет.

## Проверка за несколько минут

1. Поднять приложение по README. В «Загрузить диалоги» ввести доступную группу.
   При ошибке список прежних диалогов и оценок должен остаться.
2. Сохранить новую версию чек-листа. Открыть новый диалог; выбрать старую версию,
   запустить оценку. Во время обработки и после обновления страницы результат
   должен ссылаться на выбранную версию; изменённый глобальный чек-лист не подменяет её.
3. На диалоге с подтверждённым флагом открыть «Показать основание исходного флага».
   Через апелляцию снять флаг с причиной. Фильтр «Есть грубые ошибки (ИИ)» по-прежнему
   находит диалог; карточка показывает исходное основание и изменение финального флага.
4. Неоценённый / needs_review не попадает в «Не выявлены (ИИ)».

## Границы и оставшаяся приёмка

Браузерные тесты используют явно синтетические v2-ответы; Python-тесты проверяют
HTTP/SQLite с тестовыми адаптерами. Это не настоящий запрос Luna и не измерение
качества модели. Реальный общий прогон на собранной версии, независимая экспертная
разметка, чистый запуск на Windows и резервное видео остаются командной приёмкой.
Факты о продуктах должен утвердить капитан, неподтверждённый файл кандидатов не включён.

Существующий экспорт приложения сохранён. Схема официального `results.json`,
упомянутая в стороннем репозитории, не подтверждена первичным приложением к гайду.
До его получения не переименовываем критерии, статусы и поля по предположению и
не объявляем текущий экспорт официальным форматом сдачи.
