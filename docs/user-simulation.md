# Синтетическая проверка пользователей и диалогов

Дата подготовки: 2026-11-08. Это сценарный QA-анализ, а не реальные интервью, наблюдения за клиентами или независимый замер качества модели. Пять персон — пользователи интерфейса контроля качества; пять разговоров — отдельные учебные обращения к брокеру. Персоны не выдаются за участников этих разговоров.

Дополнительно проведён отдельный [живой прогон пяти разговоров на GPT-6 Luna](audit/synthetic-personas-2026-11-08.json): 5 завершённых оценок, по одной попытке; проверены 19 заранее заданных инвариантов, доказательства, пересчёт апелляции и перезапуск отдельной БД. Описанный ниже браузерный прогон использовал моделируемые API-ответы. Эти два вида проверки не являются измерением совпадения с закрытым эталоном Freedom.

## Состав и границы

Пакет: [fixtures/synthetic-personas.json](../fixtures/synthetic-personas.json). Он содержит пять персон в `personas`, пять импортируемых записей в `data.records` и проверяемые ожидания в `expectedObservations`. Конверт `isSuccess: true` совместим с текущим `backend.domain.normalize_import`. Это локальная учебная фикстура, а не ответ организаторов. Синтетические метки есть в ID, имени оператора, первом системном сообщении и первой реплике клиента. Реальные ФИО, телефоны, адреса, идентификаторы счетов, аудио и платёжные реквизиты отсутствуют.

При нормализации дополнительные поля `personas`, `expectedObservations`, `synthetic` и `scenario` не переносятся в разговор. Поэтому ожидания не попадают в текст, который оценивает модель, а синтетическое происхождение остаётся видно в транскрипте. ID сообщений создаются нормализатором: `<conversation_id>-m<номер реплики>`, нумерация с 1 и включает bot/system. Поле `language: RU` в смешанном разговоре отражает начальный язык; смена на KZ видна в репликах. Это проверка обработки переключения, не полный тест качества казахского языка.

Основания: [требования](requirements.md), [начальный чек-лист](../backend/rubric.json), `backend/domain.py`, `src/domain/types.ts`. Проверяем все восемь критериев через выбранные наблюдаемые инварианты. Не назначаем общий золотой итог и не утверждаем правильность продуктовой консультации без подтверждённой KB. При последующей модельной оценке фиксировать поставщика, модель, версию промпта, чек-листа и KB либо её отсутствие.

## Диалоги и ожидаемые критерии

Число в скобках — номер сообщения, не секундный таймкод. В JSON `expectedValue: null` означает ожидаемый N/A; отсутствие поля `expectedValue` означает, что точный балл не задан.

| ID | Проверяемое ожидание | Доказательство и ограничения |
|---|---|---|
| `SYN-CHAT-DISSATISFACTION` | greeting=1; discovery=1; empathy=1; closing=1 | Приветствие, представление и конкретная реакция на повторные обращения (3); уточнение до следующего шага (2–4); предупреждение об ожидании (5–6); итог и прощание (8). Заявление о передаче не доказывает реальную передачу или корректность внутреннего процесса. Точный consultation не задан. |
| `SYN-CHAT-INCOMPLETE` | discovery=1; closing=N/A; consultation не N/A по причине «нет запроса» | Уточнения (3, 5), конкретизированный запрос (4), автоматический обрыв (6). Нельзя наказать оператора за отсутствие прощания после доказанного обрыва. Точную оценку незавершённой консультации разбирать отдельно. |
| `SYN-CHAT-LANGUAGE` | greeting=1; discovery=N/A; identification=N/A; closing=1 | Первый запрос и приветствие RU (2–3), затем просьба KZ и ответ KZ (4–5), завершение KZ (7). Не требовать вопросов или идентификации для общего определения. Не превращать смену языка в самостоятельное грубое нарушение. Точную консультацию сверять с источником. |
| `SYN-CHAT-IDENTITY` | identification=0; gross-errors=0 в пределах данного текста | Сам оператор признаёт необходимость проверки (3); системное сообщение не подтверждает её (5); защищённое действие уже выполнено (6), отсутствие подтверждения признано (8). Апелляция может потребовать внешнего доказательства. Сам факт согласия не наделяется новой нормативной семантикой. Неподтверждённая идентификация не является автоматически пунктом закрытого списка грубых ошибок. |
| `SYN-CHAT-GROSS-ERROR` | greeting=0; consultation=0; closing=0; gross-errors=1 | Приветствие только у бота (2), оператор начинает с частной платной услуги (4); нет официального ответа (4–6); сам закрывает чат без прощания (6–7). Отказ клиента платить (5) не отменяет нарушения. |

Незаданные критерии всё равно должны присутствовать в полном результате оценки, но этот набор не объявляет для них жёсткий эталон. Пограничные значения шкал проверяет методолог по объяснению и источникам. В частности, отсутствие KB нельзя скрывать уверенным утверждением о продуктовой правильности. Пять случаев не дают статистически значимой точности, доверительного интервала или права заявлять процент удовлетворённости пользователей.

## Общие инварианты результата и интерфейса

1. На каждый критерий ровно один результат из разрешённой шкалы. Оценивается оператор; bot/system служат контекстом. Приветствие бота не засчитывается оператору.
2. Доказательство с цитатой указывает существующую реплику того же диалога; текст совпадает дословно, включая казахские буквы. Переход к нему не открывает другой разговор. Для отсутствующего действия показывается проверенный участок, для N/A — условие и подтверждающий участок. Указанные в фикстуре номера — подсказка проверяющему, не готовый объект Evidence.
3. У `greeting`, `empathy`, `dialogue`, `gross-errors` N/A запрещён. У остальных он допустим только при выполненном условии. Обрыв не стирает уже сформулированный запрос. Самостоятельное закрытие оператором не является обрывом.
4. Итог рассчитывает сервер: `100 * sum(weight * value / max) / sum(applicable weights)` с финальным округлением до двух знаков. N/A исключает вес из числителя и знаменателя. Нулевой знаменатель даёт отсутствие итога с причиной. Секция только из флага не имеет числового результата.
5. `gross-errors=1` обозначает наличие нарушения и отображается отдельно; вес 0 не обнуляет числовой итог. Нельзя добавить штраф за произвольный порог скорости, теги или вложения.
6. Апелляция до решения проверяющего не меняет исходные результаты. Решение имеет причину; исходная оценка, финальная оценка и привязка к версии сохраняются. Принятие и отклонение нужно различать по тексту, а не только по цвету.
7. Импорт, очередь, выполнение, ошибка, потребность в проверке и завершение не смешиваются в один статус. Неполученный результат не показывается как ноль или готовая оценка. Повторный импорт не размножает ID.
8. Ключевые действия доступны клавиатурой, фокус видим, ошибки привязаны к полям, метки не зависят от наведения или цвета. На рабочем размере экрана длинные RU/KZ-реплики и объяснения читаются без потери действий. В первую очередь проверять импорт, доказательства, апелляцию и редактор чек-листа.

## Безопасная проверка импорта без сервера и БД

Из корня проекта в PowerShell, используя существующий Python проекта:

```powershell
@'

from pathlib import Path
from backend.domain import normalize_import

path = Path("fixtures/synthetic-personas.json")
text = path.read_text(encoding="utf-8")
fixture = json.loads(text)
records = normalize_import(text)
assert len(fixture["personas"]) == len(records) == 5
assert len({r["id"] for r in records}) == 5
assert all(r["id"].startswith("SYN-") for r in records)
assert all(r["evaluation"] is None for r in records)
assert all("СИНТЕТИЧЕСКИЙ" in r["transcript"][0]["text"] for r in records)
assert normalize_import(text, existing_ids=[r["id"] for r in records]) == []
by_id = {r["id"]: r for r in records}
for case in fixture["expectedObservations"]:
    record = by_id[case["conversationId"]]
    for check in case["checks"]:
        for number in check["messageNumbers"]:
            assert record["transcript"][number - 1]["id"] == f'{record["id"]}-m{number}'
print("PASS: 5 personas, 5 unique conversations, valid evidence references, repeat import empty")
'@ | .\.venv311\Scripts\python.exe -B -
```

Этот вызов импортирует только чистую функцию нормализации. Он не запускает сервер, не открывает БД, не вызывает LLM и не создаёт оценки. Проверяет также JSON-строку — именно форму, поступающую от загрузчика. Для реального прохода интерфейса использовать отдельную временную БД и отключённые платные вызовы. Нельзя добавлять тестовые записи в рабочую БД или выдавать вручную подготовленные результаты за ответы модели.

### Найденный и исправленный дефект P2: роль системного доказательства

В первом прогоне в `src/features/Appeals.tsx:300` окно ReviewDialog использовало двоичную подпись: operator → «Оператор», всё остальное → «Клиент». Системная реплика m5 с результатом проверки личности была видна как **«Клиент · 00:18»** вместо **«Система · 00:18»**. Основная карточка диалога показывала роль правильно. Аналогичный код ошибочно подписывал бы bot.

Влияние: проверяющий видел неверный источник важного доказательства при спорной идентификации. Владелец UI исправил отображение всех четырёх ролей, аналогично ConversationDetail. Production-файлы автором проверки не изменялись. Повторный полный прогон на отдельном порту 5204 подтвердил **«Система · 00:18»**, все 12 проверок прошли, exit 0. [Снимок окна рассмотрения после исправления](../tmp/jury-ui/appeal-review.png) и report.json обновлены последним прогоном. Рабочая вкладка и backend на порту 8000 не затрагивались.
