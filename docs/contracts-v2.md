# Активный контракт CQA v2.0

Приложение обслуживает **только v2.0**. Источник истины — Pydantic-модели в `backend/contracts/v2`. JSON Schema в `contracts/v2/*.schema.json` и `src/generated/contracts.ts` создаются генератором, а не редактируются отдельно.

```powershell
.venv311/Scripts/python.exe scripts/generate_contracts.py
.venv311/Scripts/python.exe scripts/generate_contracts.py --check
```

`--check` должен завершаться успешно без изменений файлов. JSON Schema описывает структуру, но не заменяет межобъектную проверку значений, критериев и доказательств на сервере.

## Почему версия 2.0

В командной ветке уже опубликован несовместимый v1 в `contracts/v1.py`, `contracts/schemas` и `contracts/README.md`. Он сохраняется без переопределения и проверяется прежними тестами. Следующие изменения несовместимы и поэтому получили новую версию:

| Поле / граница          | Замороженный v1                   | Активный v2                                                                   |
| ----------------------- | --------------------------------- | ----------------------------------------------------------------------------- |
| Основные имена API      | `conversation_id`, `criterion_id` | `conversationId`, `criterionId`                                               |
| Тип Да/Нет              | `binary`                          | `yes_no`                                                                      |
| Значения и максимум     | JSON integer                      | десятичная строка                                                             |
| Допустимые значения     | `allowed_values: int[]`           | `allowedValues: string[]`                                                     |
| Ответ адаптера          | `AdapterResult` с `ModelOutput`   | `ModelResponse`                                                               |
| Доказательство критерия | один объект с `message_ids`       | массив объектов с `message_id` либо границами диапазона                       |
| Статус задачи           | вложенный `EvaluationJob`         | прямой `EvaluationResult`                                                     |
| Ошибка                  | вложенный `ErrorResponse`         | `ApiError` с плоскими `code`, `message`, `details`, `request_id`, `retryable` |

Смешивать поля двух версий или отправлять v1-ответ в v2 API нельзя. Для прежних числовых моделей хранилища существует явный codec в `backend/contracts/v2/codecs.py`. Mapper UI намеренно отделён от generated-типов. Это внутренние границы совместимости, а не разрешение принимать два сетевых формата. Структуры `contracts/v1.py` нельзя импортировать в новый адаптер.

## Имена и числа

Корневые DTO и тела операций содержат `schema_version: "2.0"`. Имена существующего API сохранены в camelCase. Согласованные исключения не переименовываются: `schema_version`, `message_index`, `applicability_reason`, `repair_feedback`, поля evidence и ошибки `request_id`.

Веса, `max`, элементы `allowedValues`, значения результатов и решений апелляций передаются десятичными строками. Примеры: `"0"`, `"15"`, `"0.125"`. Входные числа неотрицательны, имеют до шести дробных знаков и ограничены `1000000`; максимум критерия строго больше нуля. Экспонента, знак, ведущие нули, NaN, Infinity, JSON number и boolean не принимаются. Например, `"1e3"`, `"-1"`, `"01"`, `1` и `true` не являются допустимым весом.

Версии, количества, `message_index` и прочие целочисленные метаданные остаются JSON integer. Серверные вычисленные десятичные строки могут иметь больше шести знаков: ограничение входных шкал не переносится на промежуточный результат арифметики.

Критерий имеет `type: yes_no | scale | flag`. `yes_no` и `flag` используют `max: "1"` и `allowedValues: ["0", "1"]`. Флаг имеет вес `"0"`, запрещает N/A; значение `"1"` означает нарушение и не меняет числовой итог. Для `scale` список `allowedValues` полностью задаёт дискретные ступени: отдельного поля `step` нет. Значения численно уникальны, лежат от нуля до max и включают обе границы. Например, `"1"` и `"1.0"` — дубликаты.

N/A передаётся только как `null`. Чек-лист должен разрешать его через `allowNA` и содержать `naCondition`. В результате обязательна непустая `applicability_reason`. N/A не означает сбой API, неопределённость модели или отсутствие доказательства.

Для N/A рекомендуется явный `kind: "not_applicable"`; доказательство через проверяемую реплику `kind: "message"` также допустимо. Для применимого результата `applicability_reason` должен быть null, а `kind: "not_applicable"` запрещён.

## Сообщения и снимок входов

Backend назначает `id = {conversationId}-m{index+1}`. Первая реплика — `p1-ru-001-m1`. Считаются все роли в исходном порядке, включая bot/system. Отдельное поле `message_index` начинается с 0. Ни адаптер, ни UI не сортируют реплики по timestamp и не перенумеровывают их после фильтрации.

`EvaluationRequest` передаёт идентификатор и хеш диалога, `language`, `channel`, снимок чек-листа, сообщения, подтверждённые `knowledgeFacts` и при повторе — `repair_feedback`. Адаптер обязан использовать переданные значения, не запрашивать «последний чек-лист» во время работы и не формировать собственные ID. При изменении текста или порядка новый хеш защищает старую оценку от привязки к другой версии.

Допустимые `language`: `RU`, `KZ`, `EN`. Допустимые `channel`: `agent chat`, `voice call`; сокращения `chat`/`voice` не являются контрактом.

`KnowledgeFact` содержит `text`, `source`, `effective_date`, `product`, `jurisdiction`, `verified_by`. Пустой список фактов не разрешает выдумывать тарифы. Утверждения клиента, оператора и бота не становятся независимыми продуктовыми источниками.

Утверждённый серверный файл настраивается через `KNOWLEDGE_FACTS_PATH` и проверяется
при запуске. Его содержимое сохраняется в `EvaluationRequest.knowledgeFacts` каждой
задачи до вызова модели. Файл не поступает из HTTP-запроса оценки. Изменение файла
вступает в силу после перезапуска; сохранённые снимки задач не меняются. Формат,
проверка применимости и ограничения: [evaluation-context.md](evaluation-context.md).

## Ответ модели и доказательства

Python-интерфейс внутри FastAPI:

```python
from backend.contracts.v2 import EvaluationRequest, ModelResponse

async def evaluate(request: EvaluationRequest) -> ModelResponse:
    ...
```

Ответ модели содержит только `schema_version` и `results`. Для каждого критерия снимка нужен ровно один результат, без неизвестных ID и повторов. Значение выбирается из `allowedValues` либо равно разрешённому N/A. Модель не возвращает итог, веса, `critical`, `source_text` или отметку проверки.

Пример формы одного результата; в реальном ответе присутствуют **все** критерии снимка:

```json
{
  "schema_version": "2.0",
  "results": [
    {
      "criterionId": "greeting",
      "value": "1",
      "explanation": "Оператор поздоровался и представился.",
      "applicability_reason": null,
      "evidence": [
        {
          "kind": "message",
          "message_id": "example-m2",
          "quote": "Здравствуйте, меня зовут Анна.",
          "start_message_id": null,
          "end_message_id": null
        }
      ]
    }
  ]
}
```

Пример синтетический: такой ID и такая цитата подходят только если они действительно есть в соответствующем входе. Не используйте пример как готовый ответ для DEV.

| `kind`           | Подтверждение                                                                                                                       |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `message`        | Существующий `message_id`; если `quote` передана, она должна быть точной непустой подстрокой этой реплики                           |
| `absence`        | Проверенный включительный диапазон `start_message_id` → `end_message_id`; отсутствие действия не подтверждается придуманной цитатой |
| `not_applicable` | Реплика либо проверенный диапазон, подтверждающий условие N/A, и отдельная `applicability_reason` результата                        |

Если `quote` передана, проверяется `quote in message.text` без каких-либо преобразований. Не меняются пробелы, переводы строк, регистр, пунктуация и Unicode. При `quote: null` backend извлекает исходный текст по существующему ID; это не означает отсутствия доказательства. Пустой массив `evidence` доказательством не является. Границы диапазона должны существовать и идти в исходном порядке.

Backend добавляет `source_text`, `verification_status: verified | unverified` и `reason`. Эти поля принадлежат серверу. UI показывает исходный текст и явно выделяет непроверенное доказательство. Даже verified подтверждает текстовую привязку, а не смысловую правильность решения LLM.

## Задания и ошибки

```http
POST /api/evaluations
Content-Type: application/json

{"schema_version":"2.0","conversationId":"p1-ru-001"}
```

Настроенный оценщик принимает задание с HTTP 202. Ответ — `EvaluationResult` с ID задачи; `GET /api/evaluations/{id}` возвращает её состояние в том же формате. Публичного маршрута загрузки произвольного ответа модели из браузера нет.

| Статус              | Значение                                                                       | `score`                |
| ------------------- | ------------------------------------------------------------------------------ | ---------------------- |
| `queued`            | Снимок сохранён, задача ожидает выполнения                                     | null                   |
| `running`           | Выполняется вызов адаптера или проверка                                        | null                   |
| `completed`         | Ответ прошёл структурную, смысловую по шкале и текстовую проверку              | серверный объект Score |
| `needs_review`      | Значения-кандидаты есть, доказательство не подтверждено                        | null                   |
| `failed_validation` | Покрытие, тип, шкала или N/A не прошли проверку после разрешённого исправления | null                   |
| `failed`            | Не удалось завершить выполнение                                                | null                   |
| `retryable`         | Незавершённая задача восстановлена после перезапуска; нужен явный новый запуск | null                   |

`completed` не означает доказанную экспертную точность. При нулевом применимом весе `Score.total` остаётся null. `needs_review` не показывает предварительную арифметику как итог.

Текущий интерфейс позволяет просматривать кандидатов `needs_review`, но отдельного маршрута ручного подтверждения доказательств нет. Апелляции относятся к завершённой сохранённой оценке. Для непроверенной задачи после исправления входа/адаптера создаётся новая задача.

Неверный ID сообщения, несовпадающая цитата или отсутствующее доказательство ведут сразу к `needs_review`, без автоматического repair. Неправильное покрытие критериев, значение вне ступеней, запрещённый N/A или отсутствие его причины ведут к `failed_validation` после максимум одного repair-повтора. Общий лимит — **два вызова адаптера на задачу**, включая повторы временных ошибок провайдера, без независимого повторяющего цикла в адаптере. `repair_feedback` возвращает структурированные замечания. После исчерпания повторов ошибка провайдера имеет статус `failed`; возможность нового запуска указана в `error.retryable`.

При отсутствии `EVALUATOR_ADAPTER` POST возвращает 503, а доступность оценщика в состоянии выключена. Ключ без адаптера ничего не активирует. Ошибки клиента отклоняются до постановки задачи; ошибка уже принятой задачи отражается в её статусе и `error`. Ошибки не подменяются нулевыми баллами или N/A.

## Загрузка группы организатора

`POST /api/organizer/refresh` принимает совместимое расширение `RefreshRequest`:

```json
{"schema_version":"2.0","groupId":"CONTROL_EXAMPLE"}
```

`CONTROL_EXAMPLE` — вымышленный идентификатор, настоящий выдаёт организатор.
`groupId` — строка длиной 1–512 символов после удаления пробелов по краям.
Формат идентификатора не ограничен латиницей или предполагаемым шаблоном.
Без поля используется `DEV`; `null`, пустая строка и неверный тип дают 422.
Сервер добавляет `group_id` к настроенному `ORGANIZER_DEV_URL`, а не принимает URL от клиента.

Успешный ответ — прежний `WorkspaceState`. `dataset.group`, `dataset.total` и
`dataset.conversationIds` описывают **последнюю загруженную группу**;
`data.conversations` содержит также сохранённые предыдущие и ручные диалоги.
Поэтому длина общего списка может быть больше `dataset.total`. Для списка текущей
группы UI использует `dataset.conversationIds`; остальным записям нельзя приписывать
эту группу. Пример фрагмента ответа (остальные поля `WorkspaceState` не изменяются):

```json
{"dataset":{"group":"CONTROL_EXAMPLE","fetchedAt":"2026-11-07T12:00:00+00:00","source":"live","total":1,"conversationIds":["synthetic-control-1"]}}
```

Несовпадение группы, количества, дубликат ID или невалидная запись в ответе
организатора дают 502. Совпадающий сохранённый ID с другим содержимым даёт 409;
исходные ID не переименовываются. Все эти случаи сохраняют прежние данные целиком.
Повторная загрузка тех же данных не создаёт копии или задания модели.
Нет настроенного источника — 503. Пример полного ответа при коллизии:

```json
{"schema_version":"2.0","code":"CONFLICT","message":"Диалог с таким ID уже сохранён с другим содержимым. Набор не изменён.","details":[],"request_id":"synthetic-request-id","retryable":false}
```

`request_id` назначается сервером для каждого ответа. Подписанная ссылка и ключи
не возвращаются в ошибках. JSON Schema и TypeScript находятся в сгенерированных
`contracts/v2/RefreshRequest.schema.json` и `src/generated/contracts.ts`.

## Генерация, миграция и проверки

### Выбор сохранённой версии для оценки

`StartEvaluationRequest` допускает необязательный `checklistVersion`:

```json
{"schema_version":"2.0","conversationId":"synthetic-dialog-id","checklistVersion":1}
```

Значение — строго JSON integer 1–1000000, существующая версия из `GET /api/checklists`.
Без поля или с `null` выбирается последняя версия в момент создания задачи; это
сохраняет совместимость прежнего клиента. Строка `"1"`, bool, float, ноль и отрицательное
число дают 422 `INVALID_REQUEST`. Неизвестная версия даёт 404 `NOT_FOUND` без задачи
и вызова модели. Например:

```json
{"schema_version":"2.0","code":"NOT_FOUND","message":"Версия чек-листа не найдена.","details":[],"request_id":"synthetic-request-id","retryable":false}
```

`request_id` создаётся сервером. Успешный ответ остаётся `202 EvaluationResult`;
`checklist.version` и весь чек-лист принадлежат выбранной версии. Итог читается по
`GET /api/evaluations/{id}`. Новый глобальный чек-лист не меняет уже созданную задачу.
Старые результаты доступны по своим ID и не перепривязываются к новой версии.
Это версии одного чек-листа, не каталог разных чек-листов.

Незавершённая задача или любая апелляция по диалогу блокируют новый запуск: 409
`CONFLICT`, даже с другой версией. Прежний запрет UI теперь проверяет и backend;
для демонстрации новой версии после апелляции использовать другой диалог.

### Обновление контрактов

1. Изменить Pydantic-модель и межобъектные валидаторы в `backend/contracts/v2`.
2. Согласовать изменение с AI, backend и frontend; несовместимый wire требует новой версии.
3. Запустить генератор и добавить изменённые JSON Schema/TypeScript в тот же PR.
4. Выполнить `--check`, контрактные/property-based тесты, API-тесты и `npm run build`.
5. Проверить mapper UI: десятичная строка не должна незаметно стать итогом, пересчитанным через JavaScript float.

Проверки старого `contracts/v1.py` остаются отдельно. Их успех не подтверждает совместимость v2; миграция выполняется явно и не ограничивается переименованием `schema_version`.
