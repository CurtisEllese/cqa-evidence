# Backend v2: проверка интеграции

Эта реализация продолжает backend из main. Активные типы — `backend/contracts/v2`, схема API — `docs/contracts-v2.md`. Старый backend PR #5 использует v1 и не должен сливаться поверх v2. Перенос всего старого API не требуется: jobs, проверка доказательств, Decimal-расчёт и Repository уже реализованы в текущем приложении.

## Что проверяет backend

1. Ручной импорт доступен в пустой рабочей области без DEV URL. После импорта состояние читается из SQLite, даже если источник организатора недоступен.
2. POST `/api/evaluations` принимает `schema_version: "2.0"` и `conversationId`. Снимок текущего чек-листа и исходных сообщений сохраняется до вызова адаптера.
3. Адаптер получает `EvaluationRequest` и возвращает `ModelResponse`. Поля v1 не принимаются; значения критериев — Decimal-строки либо разрешённый null.
4. Backend проверяет доказательства и допустимые значения, затем сохраняет результат через существующий Repository. Непроверенные доказательства дают `needs_review` без score; ошибки API не превращаются в баллы.
5. Карточка диалога, GET задачи и результат после перезапуска используют один сохранённый снимок. При смене шкалы новый вызов получает новую версию, старый результат остаётся доступен по прежнему ID.

Одна задача выполняется за раз. Максимум две попытки, включая transport retry и repair, принадлежат backend; каждая попытка фиксируется в `evaluation_attempts` перед I/O. Ошибка провайдера сохраняется безопасным кодом без текста исключения. Задержка Retry-After больше 30 секунд не сокращается: задача получает явную ошибку с возможностью нового запуска. Глобальный интервал стартов не менее 5 секунд и отключение скрытых SDK-повторов должен обеспечить общий экземпляр Gemini-адаптера.

## Проверка за две минуты

После установки зависимостей из README:

```sh
npm run contracts:check
npm test
npm run build
```

Сервис запускается `npm start`. Для импорта единственного синтетического диалога:

```sh
curl -sS http://127.0.0.1:8000/api/import -H 'Content-Type: application/json' --data-binary @backend/tests/fixtures/v2-import-request.json
curl -sS http://127.0.0.1:8000/api/evaluations -H 'Content-Type: application/json' --data-binary @backend/tests/fixtures/v2-evaluate-request.json
```

При подключённом v2-адаптере второй запрос возвращает HTTP 202 и ID задачи. Подставьте полученный ID в `GET /api/evaluations/{id}`. Без адаптера ожидается HTTP 503; это не проверка реального Gemini. Для повторного импорта используйте новый conversation_id: существующий диалог намеренно не перезаписывается.

После завершения задачи перезапустите сервис с тем же `DATABASE_PATH`. GET задачи и `/api/state` должны вернуть сохранённый результат без нового обращения к модели. Затем измените критерий через редактор, сохраните версию и запустите новую оценку.

## Границы проверки

Автотесты используют только синтетические ответы внутри tests. Проверяются RU/KZ/EN, ISO-метки звонка, исходные ID всех ролей, 85.38, новая шкала 0/2/5, ошибки/repair, сохранность результата и лимит вызовов. Это проверка backend-контракта, а не качества Gemini или совпадения с Ground Truth.

Реальный SDK-вызов и промпт остаются в зоне Adalbala. Для живого запуска нужны совместимый v2-адаптер и ключ в локальном окружении сервера. Этот PR не добавляет провайдер, новые поля контракта, апелляции или частичный пересчёт. Секции нормируются отдельно внутри секции — соглашение команды, их проценты не складываются.
