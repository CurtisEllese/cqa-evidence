# Независимая проверка оценки Freedom Quality

Версия процесса: `human-evaluation-1`, 8 ноября 2026. Это воспроизводимый процесс получения и сравнения человеческой разметки. Скрытый эталон Freedom не предоставлен и не воспроизведён. Существующие DEV-результаты и синтетические ожидания не являются эталоном.

## Кто и что готовит

Владелец данных формирует обезличенную выборку реальных разговоров с законным доступом к исходным сообщениям и аудио, если оно требуется. Для каждого случая обязательны `caseId`, `sourceKind` (`real`/`synthetic`), `sourceReference` (происхождение), `split` (`calibration`/`holdout`) и полный `request` по EvaluationRequest v2. Случаи с разными версиями чек-листа сравниваются отдельными отчётами. Из запроса исключается `repair_feedback`; результаты модели вообще не входят в пакет разметки.

В выборке отдельно представлены RU/KZ/EN и нужные каналы. Для казахского нужен эксперт, способный оценивать оригинал, включая переключение языков. Не переводить сообщения для удобства оценщика и не делать из ASR-пунктуации оценку дикции. Отдельно включить реальные ошибки, редкие критические нарушения, N/A, неполные сведения о продукте, действия бота, исправления оператора и неоднозначные случаи. Выборка с намеренно повышенной долей критических ошибок полезна для диагностики, но не для оценки их распространённости в потоке.

Капитан согласует версию рубрики, допустимые баллы, критические флаги, условия N/A, критерии приёмки и план выборки **до** просмотра holdout-ответов. Число случаев и минимальный recall критических нарушений нельзя выдавать за требования организатора без его документа. Маленькая пилотная выборка помогает исправить инструкцию, но не доказывает производственную accuracy. После калибровки рубрика замораживается; отложенные разговоры и их близкие дубликаты не используются при правке промпта.

## Рабочий порядок

1. Подготовить JSON-массив случаев. Источник `real` назначает ответственный владелец данных, не модель. Скрипт вычисляет SHA-256 всего случая и отдельный hash чек-листа; внешнего `conversationHash` недостаточно. Входные JSON ограничены 20 MiB.
2. Создать отдельные слепые пакеты для экспертов A и B. Их идентификаторы псевдонимны, но владелец хранит приватную связь с реальными людьми и квалификацией. Эксперты не видят ответы модели или друг друга. Пустые шаблоны намеренно не проходят импорт.
3. Эксперты заполняют каждое суждение по оригиналу: `status`, `value`, `reason`, `messageIds`, `sourceRefs`. `assessed` + `null` означает только обоснованное N/A по рубрике. `unassessable` + `null` означает нехватку доказательств; это не ноль и не N/A. Для отсутствия действия перечисляют проверенные сообщения и описывают проверенный диапазон в `reason`. Указать проверяемый источник и его применимость для продуктового вывода; фраза оператора не является независимым подтверждением.
4. Импортировать независимые разметки. У каждого человека может быть только одна запись на случай. Повторные ID, неизвестные сообщения, изменённый текст/рубрика, недопустимые баллы, N/A без разрешения и отсутствие обязательных полей отклоняются. Правки оформляются новым согласованным набором с новым отчётом; исходники не перезаписываются.
5. Третий эксперт C разрешает разногласия и подтверждает совпадения, оставаясь слепым к модели. Запись `phase=adjudicated`, `independentOfOtherAnnotators=false`, `basedOn` содержит ID обеих независимых разметок. Объединённый импорт содержит A, B и C. Время решения не может предшествовать исходным разметкам. Не применять автоматическое большинство как «истину».
6. Заморозить эталонный набор с подписью/receipt владельца. После этого экспортировать сохранённые предсказания одной версии GPT-6 Luna; скрипт не запускает модель. Для каждой prediction нужны `caseId`, `caseHash`, `rubricHash`, `model=gpt-6-luna`, `promptVersion`, `runId`, `values` с полным покрытием критериев. Запрос, rubric и hash должны быть теми же, на которых получен результат. Нельзя приписывать новый hash старому несовместимому ответу. Частичные/неуспешные ответы оставляют без prediction и отражают как пропуск.
7. Сравнить, разобрать ошибки по конкретным ID, согласовать изменения на calibration. Повторная настройка по holdout означает, что он больше не независимый holdout.

## Команды без API

Запуск из корня проекта, каждый output — новый путь:

```powershell
node scripts/python.mjs scripts/expert_evaluation.py prepare --cases cases.json --annotator expert-A --output packet-A.json
node scripts/python.mjs scripts/expert_evaluation.py prepare --cases cases.json --annotator expert-B --output packet-B.json
node scripts/python.mjs scripts/expert_evaluation.py import --cases cases.json --labels labels-A-B-C.json --output validated-labels.json
node scripts/python.mjs scripts/expert_evaluation.py report --cases cases.json --labels validated-labels.json --predictions frozen-predictions.json --output comparison.json
```

Пакет содержит `cases` и `labels`. Для импорта передать **массив** заполненных labels, не весь пакет. Формат JSON сохраняет Unicode и различает null от строки `"null"`. Ошибки CLI не выводят личные данные. `report` без `--labels`/`--predictions` допустим и честно покажет отсутствие эталона/сравнения. Скрипт не читает SQLite, `.env`, API-ключ или DEV-кэш, не обновляет продукт и не перезаписывает существующий output. Это отдельный offline-процесс; интерфейс импорта в UI не реализован.

## Как читать отчёт

`slices` строго разделяет real/synthetic, calibration/holdout и RU/KZ/EN. Для каждой пары экспертов показаны exact agreement и Cohen’s kappa **по каждому критерию**, agreement критического признака и MAE итоговых баллов. Одна пара экспертов не смешивается с другой; N/A и unassessable — отдельные категории. Номинальная kappa не учитывает размер различия баллов и при вырожденных маргиналах равна null, а не 1.

Модель сравнивается только с adjudicated, а не с собственным ответом или большинством. Есть расхождения по критериям, MAE/max absolute error итогового балла, TP/FP/TN/FN критических нарушений, precision/recall с явными знаменателями и покрытие. При отсутствии положительных примеров recall — null. При отсутствии предсказанных положительных precision — null. Флаги не добавляют вес к итоговому баллу. Для N/A веса перенормируются; при неизвестном взвешенном критерии итоговая пара не сравнивается. Неразмеченные/неоценимые случаи не превращаются в правильные ответы.

Итоговые баллы рассчитываются заново по замороженной рубрике; это сравнение решений, а не проверка сериализованного production total. Корректность production scoring проверяется его отдельными тестами. Доверительные интервалы и поправки на дизайн выборки пока не реализованы; не трактовать малые или зависимые выборки как точную оценку популяции.

Даже валидный импорт не доказывает личность, квалификацию, независимость, полноту фактических оснований или честность `sourceKind`. Для этого нужен аудит владельца данных и записи экспертного согласования. Поле `accuracyClaim` без реальных adjudicated labels — `not_established`; при их наличии допускается только сравнение на указанной выборке, не заявление о скрытом эталоне Freedom.
